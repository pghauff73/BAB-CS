# BAB-CS HTML Documentation Redesign and Rewrite Plan

## Objective

Redesign the generated HTML documentation so it communicates the engineering
value and limits of Bounded-Authority-Based-Circuit-Simulation (`BAB-CS`) in a
professional, modern, and educational form. Every rendered Markdown document
must help a novice understand newly introduced acronyms and core numerical
concepts without weakening the technical claim boundaries.

## Authoritative Scope

The scope is the complete generated document tree:

- every Markdown file directly under `docs/`;
- `docs/html/index.html`, `docs/html/styles.css`, and `docs/html/app.js`;
- the deterministic payload generated by `tools/build_docs_html.py`;
- the generated Scalable Vector Graphics (`SVG`) diagrams;
- documentation tests in `tests/test_docs_html.py`; and
- browser behavior for desktop, mobile, print, search, navigation, citations,
  and direct `file://` use.

## Requirements

1. Present an engineering-critical hero explaining why a plausible waveform may
   still be numerically untrustworthy.
2. List engineering projects suited to BAB-CS and state the evidence and boundary
   for each project.
3. Compare BAB-CS with specialist simulation software as a workflow map, not a
   ranking.
4. Rewrite the five current-work essays in professional, novice-readable prose.
5. Expand each acronym on first educational introduction within a document.
6. Explain each core numerical concept in plain words when it is introduced.
7. Preserve technical formulas, citations, claim boundaries, exact case names,
   release authority, and reduced-order classifications.
8. Keep all generated output deterministic and all bracketed references
   clickable.
9. Verify all Markdown documents, not only the landing page and essays.

## Educational Contract

Each non-home document will receive a generated **Document Learning Guide**.
The guide lists every recognized acronym and core concept used by that document,
with a short plain-language explanation. The first visible occurrence of each
recognized term in the rendered prose will be marked with an accessible
definition. Code blocks, links, identifiers, and source text remain unchanged.

This generated layer complements source rewriting. It does not replace the
inline explanations already written into the five essays, and it does not alter
the underlying Markdown evidence.

## Implementation Plan

### Phase 1: Information Architecture

- retain the searchable complete document tree;
- use an engineering-decision hero rather than a product-only introduction;
- add a novice concept guide, engineering challenge summary, project portfolio,
  workflow diagram, simulator comparison, evidence surface, and claim boundary;
- preserve responsive navigation, table of contents, theme, print, and copy-link
  behavior.

### Phase 2: Essay Rewrite

- rewrite `CURRENT_WORK.md` around purpose, authority, evidence, projects, and
  limits;
- rewrite `NUMERICAL_METHODS_ESSAY.md` around equations, candidate methods,
  correction, bounds, replay, phase, and energy;
- rewrite `ENGINEERING_AND_PERFORMANCE_ESSAY.md` around numerical ownership,
  dense and sparse execution, measured optimization, and rejected shortcuts;
- rewrite `VALIDATION_RELEASE_AND_CLAIMS_ESSAY.md` around evidence layers,
  external comparison, deterministic artifacts, and human approval; and
- rewrite `APPLICATIONS_AND_RESEARCH_ROADMAP.md` around suitable projects,
  software handoffs, and staged research.

### Phase 3: All-Document Learning Layer

- define one deterministic concept glossary owned by the documentation builder;
- detect which glossary concepts occur in each Markdown document;
- include those concept identifiers in the generated payload;
- render a compact learning guide for each non-home document; and
- annotate the first prose introduction of every detected concept.

### Phase 4: Verification

- test exact coverage of every `docs/*.md` file;
- test glossary ownership, uniqueness, and acronym coverage;
- test that every non-home document with recognized terms receives a guide;
- test first-introduction annotation behavior in a browser-capable JavaScript
  environment where available, and syntax plus source-contract behavior
  otherwise;
- regenerate the payload and SVG assets twice to prove byte determinism;
- run the complete Python suite, JavaScript syntax check, Python compilation,
  generator check mode, and whitespace validation; and
- inspect desktop, mobile, long-page, and direct SVG rendering.

## Completion Criteria

The redesign is complete only when:

- every explicit requirement above has direct source or runtime evidence;
- all current `docs/*.md` files appear exactly once in the HTML tree;
- every recognized novice concept used by a document appears in that document’s
  generated learning guide;
- first concept introductions are visibly and accessibly annotated;
- the five essays remain rewritten and technically bounded;
- all generated artifacts are current and deterministic;
- desktop and mobile rendering show no overlap or navigation crowding; and
- the complete repository test suite passes, with optional skips reported rather
  than treated as successes.
